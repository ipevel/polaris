## 1. 结论与必须知道的三件事

**这个系统在"客户端能控制的范围内"把安全边界做得很紧**：配置在进入内核之前被逐行清洗并失败关闭；凭据只发往白名单主机；面板地址完全由用户掌控、App 不内置任何地址；会话失效的判断刻意避免了 CDN 拦截导致的误登出。

但有三件事必须先说清楚，否则后面的走查会被误读：

1. **面板是外部系统，服务端行为整体不可见。** 本仓库能确认的只有客户端"请求什么、怎么解析"，无法确认额度扣减、套餐生效、订单结算的真实规则。所有相关结论在图上都保持 `[未知]`。
2. **配置净化是单点安全防线。** 面板可以指定任意 https 域名作为订阅来源（只校验 scheme，不校验 host），该内容随后直接进入净化器。净化器一旦有漏洞，没有第二道校验兜底。
3. **代码里存在一条绕过净化的路径，当前不可达。** `ProfileProcessor.update()` 会无条件直抓订阅并热重载，不脱敏。仓库内逐项核验确认它没有生产者（详见 `first-connect-flow.evidence.md` 第 9.1 节），但它没有编译期/CI/测试防线，也没有在 agent 指令里标注"不可用"。**这是本报告识别出的最高优先风险**，且修复成本极低。

## 2. 系统上下文（L1）

```
用户 ──▶ Polaris App（主进程：UI / 网络 / 配置生成）
              │                              │
              │ HTTPS / REST（凭据仅发白名单主机）  │ Binder / AIDL(KAIDL) + 广播 + ContentProvider
              ▼                              ▼
      用户自选面板（外部）            mihomo 内核（:background 及服务进程）
      XiaoV2b / Xboard               └─ TUN 转发 · 配置装载 · 秒级流量心跳
      【信任边界外】                     【独立进程 · 本机内】
```

- 面板是**用户自己填的**，App 不内置、不兜底任何地址（`ApiUrlStore.kt:26-33`）。
- 内核是**独立进程**，跨进程能力通过 KAIDL 生成的 AIDL 接口 + 广播 + 3 个 ContentProvider 暴露（非 `.aidl` 手写文件）。
- 「流量」在本系统里有**两条互不相干的链路**：内核侧本机实时统计，与面板侧按日用量。混谈这两者是最容易犯的理解错误。

## 3. 业务流走查（actor / action / outcome）

> 图：`first-connect-flow.business.dot`。以下每步均在 `first-connect-flow.evidence.md` 有代码级证据。

### 3.1 用户提供面板地址（触发点）

用户填写**自己**的面板网址。客户端做两件事：

- **归一化与校验**：必须能归一化为合法 https 地址，否则就地报错，不发任何请求。
- **变更确认**：若新地址与已保存的不一致，先弹二次确认，避免误切面板导致登录态与订阅全部错配（`LoginViewModel.kt:116-126`）。

结果：地址与后端类型写入加密存储，网络层在**请求期**实时读取，改完无需重启进程即生效（`ApiUrlStore.kt:47-49`、`BackendAdapterFactory.kt:129`）。

### 3.2 客户端识别面板类型

面板有两套后端（XiaoV2b / Xboard），请求路径与字段不同。类型未知时，客户端先对 `{面板}/api/v1/guest/comm/config` 发一次探测请求，按响应字段判定类型。

- **值得注意的安全设计**：私有/保留地址**不自动探测**，防止 SSRF（`LoginViewModel.kt:393-395`）。
- 探测失败则中止登录并明确报错，不猜测类型（`LoginViewModel.kt:259-268`）。

结果：路径与字段格式确定下来，后续请求才可能成功。

### 3.3 用户用账号密码换取访问凭据

- 客户端按已识别的类型选适配器（两套适配器在进程内同时实例化，每次请求按当前类型路由，切换后端无需换包）。
- **凭据注入闸门**：只有目标是白名单主机、或正是当前用户填写的面板主机（含子域）时，才附加 `Authorization`。非白名单主机记一条警告日志后**不带凭据发出去**（`AuthInterceptor.kt:88-114`）。
- 拦截器顺序被刻意安排为"先按运行时面板地址改写主机，再判白名单"，因此判定的对象是正确的目标主机。

结果：登录态落在本地加密存储，订阅缓存被清空以强制拉取新账号的数据。

### 3.4 客户端读取套餐与额度

- 带 TTL 缓存和互斥锁，避免并发重复请求；并在响应回来时**二次校验会话未切换**（防止切换账号后旧响应污染新会话）。
- 领域换算：`usedTraffic = upload + download`。
- **无有效套餐时，连接开关根本不启动**，改为提示并引导续费。

结果：用户看到套餐名、已用流量、到期时间；系统据此决定"能不能连"。

### 3.5 客户端取得面板下发的代理配置

- 候选地址按优先级：**账号下发的订阅地址（必须是 https）** → 兜底用 `面板地址 + SUBSCRIBE_PATH + ?token=`。
- 逐候选尝试，任一失败继续下一个；全失败才报错。这条回退是修过的缺陷——此前只取单个地址，面板换域名后旧域名停用就永远拿不到订阅（`SubscribeSourceImpl.kt:87-105` 的注释记录了这次修复）。
- 顺带从响应头 `profile-title` / `profile-web-page-url` 捕获站点品牌信息。

结果：拿到订阅原文（第三方可控文本），进入净化环节。

### 3.6 客户端把配置净化为安全配置（本流程的安全核心）

这是整条链路最值得投入注意力的一步：

1. 响应体先过 **20MB 上限**（超限拒绝）和有效性判定（非空、无控制字符、不是 HTML/JSON、必须含订阅入口键）。
2. 逐行清洗：剥离 BOM → 顶层键去缩进 → 引号键归一 → **清零顶层端口** → **中和控制面** → 清理 subtitle 模式 → 注入健康检查配置 → **注入白名单直连规则 + FakeIP 过滤**。
3. **失败关闭**：任一关键步骤出错，或清洗后仍残留危险顶层键 → 直接返回空串，放弃输出，上游因此不写文件。
4. 净化后的文本以"临时文件 + `fsync` + rename"原子写入本机。

结果：一份"面板无法通过订阅投毒把客户端变成开放代理或任意端口监听"的配置落到本机。

### 3.7 内核装载配置 → 建立 TUN 隧道 → 用户看到已连接

- 客户端写盘后**跨进程通知**内核"配置已变更"；内核侧的配置模块收到广播后装载该 uuid 的配置，回写选择器状态与当前 profile 名，并回报"已装载"。
- 若配置内容与上次**完全一致，跳过内核重载**（避免无谓重启隧道）。
- 起隧道前 UI 有三重闸门：**有套餐 → 申请通知权限（Android 13+ 前台服务通知） → 系统 VPN 授权弹窗**。
- `VpnService` 在独立运行时循环里维护 TUN（地址、路由、DNS、应用黑白名单、IPv6 开关），并支持"切换 TUN 堆栈原地重建"。
- **就绪是异步的**：客户端不把"内核进程已启动"当作可用，而是轮询隧道状态直到真正就绪；期间 UI 保持"连接中"且**允许用户取消**（这段逻辑的注释记录了一次"按钮关不掉、用户只能杀 App"的历史缺陷）。

结果：隧道可用，UI 切换为已连接并开始计时。

### 3.8 流量回流（两条链路，勿混）

**链路一 · 本机实时**：内核侧每秒做一次累计差值快照（blip）；客户端直接读这个秒级快照来显示网速，而**不用自己的轮询间隔做差分**——因为 AIDL 往返会让真实间隔变成 1.0~1.2s，差分法会系统性低估网速（`MainViewModel.kt:127-130` 注释明确解释了取舍）。累计值用于"本次会话已用流量"。

**链路二 · 面板侧按日**：另起一条请求到面板取按日用量明细。与链路一在数据来源、口径、刷新时机上完全不同。

### 3.9 失败路径（图上的抵扣分支）

| 情形 | 系统行为 | 设计意图 |
| --- | --- | --- |
| 面板不可达 | 候选地址逐个回退，全失败才报错 | 面板换域名不至于永久失联 |
| 响应不是有效订阅（已过期/HTML 错误页） | 拒绝写入 | 不让错误页变成配置文件 |
| 净化未通过 | 拒绝写入，失败关闭 | 宁可不可用，不用半清洗配置 |
| 无有效套餐 | 阻止连接，引导续费 | 不把无效状态暴露成"连不上" |
| 隧道长时间未就绪 | 保持"连接中"，可随时取消 | 用户始终有出口 |
| 会话失效 | 仅当"面板 JSON + 失效关键词"才清会话并停 VPN | 见下 |

**会话失效判定值得单独表扬**：401 一律视为失效；403 则必须先确认"响应是面板自己的 JSON 且含失效关键词"。CDN/WAF 返回的 HTML 拦截页与空响应**一律不算失效**——否则一次边缘拦截就会让用户被清会话、停 VPN，彻底锁在门外。注释记录了 2026-09-20 的线上事故正是此因（`AuthInterceptor.kt:37-43`）。

## 4. 数据与状态摘要

| 记录 | 存储 | 生命周期与边界 |
| --- | --- | --- |
| 面板地址 + 后端类型 | 加密 SharedPreferences（`ApiUrlStore`） | 登录提交时写入；改完下一次请求生效；无内置默认值 |
| 登录态 + 账号信息 | `SessionStore` / `SessionManager`（`SessionState.LoggedIn`） | 登录成功建立；401/403(面板失效) 或登出清除，登出同时停 VPN |
| 账号密码（可选"记住我"） | `CredentialStore`（加密） | 勾选记住才保存；否则清除 |
| 领域订阅信息 | `SubscribeRepository` 内存 TTL 缓存 + `SessionStore` | 登录时清缓存；拉取成功后落一份 |
| 面板下发的配置原文 | 内存（临时） | 只存在于下载到净化之间，不落盘 |
| **净化后的配置** | `filesDir/imported/<uuid>/config.yaml`（首次先 `pending/` 再 commit） | 原子写；内容不变则不重载；同账号旧 profile 与 24h 过期 pending 会被清理 |
| profile 记录 | 内核侧 `Imported` / `Pending` Dao（**明文库**） | **刻意不落订阅 token**（`source` 不含 token），这也是内核无法自行重构订阅请求的原因 |
| 配置加密键 `ageSecretKey` | profile 记录字段 | 供内核侧配置加解密使用；生成与注入链路本次未完整追（见缺口 C4） |
| 内核实时流量 | 内核进程内存（Go 原子计数器） | 每秒 Swap；隧道断开清零会话字段 |
| 面板侧按日用量 | 不落本地，按需请求 | 口径由面板决定（未知） |

**事务边界提示**：配置写入是"原子写单文件"，但"写盘成功"与"内核成功装载"是**两个独立阶段**，中间靠广播衔接，不存在跨进程事务。因此存在"文件已更新而内核装载失败"的窗口——代码通过"内容一致则跳过重载"和"装载失败不抛异常（避免 VPN 静默断开）"来降低影响面。

## 5. 关键技术机制（需要改代码时再看）

完整实现级视图见 `first-connect-flow.technical.dot`。这里只列最容易踩坑的几条：

- **双后端不是编译期开关**：两套适配器同时存在，按运行时持久化的 `backendType` 每次请求路由；没有兜底默认值，由登录流程保证提交前已写入（`DualBackendAuthApi.kt:29-44`）。
- **主机改写发生在拦截器链最前**：静态 baseUrl 只决定 Retrofit 建请求时的起始主机，真实主机由 `ApiFailoverInterceptor` 按运行时面板地址改写（`BackendAdapterFactory.kt:110-130`）。
- **配置生成全程在 IO 线程并持互斥锁**：订阅下载 + 行级清洗是 CPU 密集操作，数 MB 配置可达数秒；留在主线程会冻结 UI 并把锁占住，表现为"连接卡死、按钮关不掉"（`KernelConfig.kt:58-66` 注释）。
- **profile 身份由 email 的 SHA-256 派生**（`Polaris-<sha256>`），`source` 为面板地址 + 订阅路径。这解释了为什么"同一账号换面板"会触发旧 profile 清理。
- **跨进程通知是"广播 + ContentProvider"**：变更用广播，连接状态用 `contentResolver.call(StatusProvider.METHOD_CURRENT_PROFILE)` 查询（`KernelManager.kt:216-238`）。

## 6. 未知与假设

**假设（本次报告依赖、但未验证的前提）**：
- 假设面板的 `/api/v1/guest/comm/config` 与订阅接口行为与其客户端契约一致；
- 假设编译产物即运行行为（无未提交的反向定制）。

**明确未知**：见 `first-connect-flow.risks-and-gaps.md` 的 C 节（面板侧计费规则、`remote.json` 分发细节、应用内更新校验链路、`ageSecretKey` 全链路、端到端测试覆盖、危险键清单与内核版本对应关系）与 A2 节的运行时未观测项。

**本报告未覆盖**：礼品卡、邀请返利、工单、公告、订单支付、应用内更新。它们是同一产品的其它流程，混进本图只会让安全主线失焦。

## 7. Agent 指令覆盖度

仓库包含一套发版与合规流程约定，**强在发版与合规流程，弱在业务与安全约束**。对本流程而言，它没有写进以下 4 条，而这 4 条恰好是避免事故的关键：

1. 净化链路是安全底线，任何路径都不得绕过 `SubscriptionSanitizer`；
2. `ProfileWorker` / `ProfileProcessor.update()` 是**保留且不可达**，不要再接调度方；
3. 面板是外部系统，服务端行为不可假定；
4. 订阅刷新时机是"进入仪表盘触发"，不是定时器。

## 8. 下一步建议

按性价比排序，详见 `first-connect-flow.risks-and-gaps.md` E 节：

1. 处置 `ProfileProcessor.update()`（删除，或加 CI 守卫）——最高优先，成本最低；
2. 确认 `ProfileReceiver` 的权限模型与同签名面；
3. 核对净化器危险键清单与当前内核版本的差距；
4. 与产品确认长期挂机场景是否需要时间驱动的订阅刷新；
5. 确认降级路径（直连域为空）是否有用户可见提示。
