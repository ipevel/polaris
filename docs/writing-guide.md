# 说明规范

本规范约束本仓库的**提交信息（commit message）**与**所有 Markdown 文档**，目的是让历史可读、文档一致、协作者（含 AI 辅助流程）写出可预期的内容。

> 适用范围：所有提交者与自动化流程。提交前自查清单见[第三节](#三提交前自查清单)。

---

## 一、提交信息规范

### 1.1 格式

```text
<type>(<scope>): <摘要>

<正文：为什么 / 影响 / 如何验证>

<页脚：BREAKING CHANGE / Closes #123>
```

- `<scope>` 可省略（省略时写作 `<type>: <摘要>`）。
- 标题与正文之间空一行；正文与页脚之间空一行。

### 1.2 type 取值

| type | 含义 |
|---|---|
| `feat` | 新功能 |
| `fix` | 缺陷修复 |
| `docs` | 仅文档改动 |
| `style` | 不影响行为的格式 / 风格调整（含格式化） |
| `refactor` | 重构（不新增功能、不修缺陷） |
| `perf` | 性能优化 |
| `test` | 测试相关 |
| `build` | 构建系统与依赖（Gradle、NDK、CMake 等） |
| `ci` | CI 配置与脚本 |
| `chore` | 杂项（版本号、远程配置等） |
| `revert` | 回滚既有提交 |

### 1.3 scope（可选）

建议取值：`app`、`ui`、`nodes`、`routing`、`home`、`traffic`、`update`、`config`、`kernel`、`ci`、`repo`、`release`、`deps`。新增模块时保持一致、简短、小写。

### 1.4 标题（摘要）

- 用中文祈使句概述"做了什么"。
- 整个标题 ≤ **50 字符**（含 `type(scope): `）；细节放进正文。
- 结尾不加句号；不使用全角破折号 `——`。
- **禁止以 BOM（U+FEFF）或零宽字符开头**（历史上出现过导致首字乱码）。
- 不使用 `Update xxx` 这类无信息量标题。

### 1.5 正文与页脚

- 说明"为什么改 / 影响面 / 如何验证"，不要复述 diff。
- 每行建议 ≤ 72 字符；多个要点用 `-` 列表。
- 破坏性变更写入页脚：`BREAKING CHANGE: <说明>`。
- 关联 Issue：`Closes #123` / `Fixes #123`。

### 1.6 纪律

- **一次提交只做一件事**；不要把一个标题塞进多个 scope（`feat(nodes,routing,ci): …` 是反例）。
- 同一个标题不要重复用于多个提交；确实分批时在正文里区分。
- 可选：复制 `.gitmessage` 并执行 `git config commit.template .gitmessage` 启用模板。

### 1.7 正反例

反例：

```text
Update README.md
feat(nodes,routing,ci): 节点页重构 + 延迟测速修复 + CI 调整
```

正例：

```text
feat(nodes): 重构节点页为两层选择

主组与分流组改为同层可选，卡片收起后仍显示当前出口。

验证：本地九项门禁全绿；真机切换出口生效。

Closes #42
```

## 二、文档写作规范

### 2.1 语言与术语

- 正文用简体中文；代码、命令、路径、文件名、专有名词保留原文。
- 中英文之间、数字与中文之间加空格（如 `Android 8.0`、`使用 Git 管理`）。
- 术语统一：`Polaris`（项目名，不写作"北辰"）、`mihomo`（内核）、**面板**（XiaoV2b / Xboard）、**节点**、**订阅**、**分流**、**规则组**、`versionCode`。
- 缩写首次出现时给出全称。

### 2.2 结构

- 每个文件仅有一个一级标题 `#`。
- 标题层级逐级递减，不跳级（`##` → `###`）。
- 开头一段概述说明"这篇讲什么、给谁看"。
- 长文按"总—分"组织，必要时加目录。

### 2.3 代码与命令

- 一律使用围栏代码块并标注语言（`bash` / `json` / `kotlin` / `kts` / `xml` / `ini` / `text`）。
- 命令默认在**仓库根目录**执行；需要特定目录时显式 `cd`。
- 示例值用占位符（`<你的域名>`、`example.com`），禁止真实值。

### 2.4 链接、表格与图示

- 仓库内文件用相对链接（如 `[CONFIG](CONFIG.md)`）。
- 外部链接用完整 URL；改动文档时保持锚点链接有效。
- 对照关系用表格；图示优先用可 diff 的文本源（如 `.dot`）。

### 2.5 单一事实源

各文档职责如下，避免重复维护易变信息：

| 文档 | 视角 |
|---|---|
| `README.md` | 用户：介绍、下载、编译、配置入口 |
| `CONTRIBUTING.md` | 贡献者：门禁、代码规范、提交规则 |
| `CONFIG.md` | 部署者：构建配置与远程配置字段 |
| `SECURITY.md` / `SUPPORT.md` | 安全报告 / 求助渠道 |
| `docs/` | 设计与架构说明 |

- 版本号与默认值以**代码为准**（`app/build.gradle.kts`），不要在多处手工复制。
- 发布流程自动维护的字段（`config/remote.json` 的更新字段）不在文档里手工抄写。
- 改动功能或流程时，同步更新对应文档。

### 2.6 禁止出现的内容

- 任何密钥、token、密码、签名材料。
- 真实面板地址、自持域名、私人邮箱、内网地址。
- 本机绝对路径（如 `C:\Users\...`、`C:\Android\Sdk`）。
- 真机测试截图与构建产物。
- BOM（U+FEFF）等不可见字符。

## 三、提交前自查清单

- [ ] 提交信息符合[第一节](#一提交信息规范)：`type(scope): 摘要`、标题 ≤ 50 字符、无 BOM、一次只做一件事。
- [ ] 关联文档已同步更新（`README.md` / `CONTRIBUTING.md` / `CONFIG.md` / `docs/`）。
- [ ] 文档内无密钥、真实域名、本机路径、测试截图。
- [ ] 本地全量门禁全绿（见 [CONTRIBUTING.md](CONTRIBUTING.md)）。
